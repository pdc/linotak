How to mitigate [Server-Side Request Forgery] risks on a site that scans URLs
in response to user input?

## Risks

One of the reasons for [replacing my elderly Svelte code] with TypeScript written
with the fewest possible dependencies is to reduce the deluge of Dependabot
alerts. So now I am pondering a [code scanning alert] that is about Linotak’s
handling of URLs.

The issue here is that part of processing a new note is to find URLs in the note,
create entries in the database for them, and scan them for a page title and other
metadata. The scanner does a GET request on the URL without further checking.

On a system with internal backend services this poses a risk because the URL
is accessed from a computer within the internal network, allowing access to
resources that are supposed to be inaccessible to outsiders.

In the case of Linotak the risk is partially mitigated:

- The only URLs recognized in notes are HTTP and HTTPS (and not for example
  the `file:` scheme, which would allow access to internal server files);
- Only a few HTML fragments from the target resource are exposed on the site;
- There is no way for outsiders to sign up as users, so the only people with write
  access are editors whom the site owner presumably knows;
- Nothing goes public without editorial review.

The latter two protections are useless if an attacker can acquire an editor’s
login credentials.

The regexp for URLs does allow for URLs with IP addresses instead of domain names,
however, which would allow internal and loopback addresses to be smuggled in.
The structure of the rest of the URL is barely examined at all.

Another thing to consider—though I think it is probably a different CVE category—is
whether some attacker with editor access might use it as a way to send a malformed
URL to a target site that their web browser would not permit?

## Changes

We’re adding a new function called `fetch` for retrieving public web pages. It only
needs to support GET, does not need cookies or fancy headers or authentication.
It replaces using `requests.get`.

Some of the assumptions about the URLs could be explicitly checked as part of
the code path the CodeQL test has identified as vulnerable:

- Start with the [Validators] package’s URL check
- Parse with Python’s URL parser
- Explicitly check it is HTTP or HTTPS;
- Insist on domain names not IP addresses and [validate domain name];
- Check none of the IP addresses the domain resolves is [internal or loopback];
- Forbid access to internal domain names somehow (even if my set-up does not
  at present have internal REST services, I don’t want it to be a security liability
  in other contexts); and
- Can we do any useful syntax validation on the URL path and query string?

The other thing we can change is to call `requests.get` with `allow_redirects=False`,
so that we can apply the same validation to the redirected-to URLs as we do to
the initial URL.

## Implementation

The [Validators] package was new to me. It is linked to from the  [OWASP Cheat Sheet],
which I am taking as a vote of confidence. To my slight surprise it already seems
to cover several of the above points. The signature of the URL validator is as follows:

```python
def url(
    value: str,
    /,
    *,
    skip_ipv6_addr: bool = False,
    skip_ipv4_addr: bool = False,
    may_have_port: bool = True,
    simple_host: bool = False,
    strict_query: bool = True,
    consider_tld: bool = False,
    private: Optional[bool] = None,  # only for ip-addresses
    rfc_1034: bool = False,
    rfc_2782: bool = False,
    validate_scheme: Callable[[str], bool] = _validate_scheme,
):
    ...
```

So it looks like some of the protections we want are already provided. The exception
seems to be that while it rejects explicit references to local addresses (as in
`http://127.0.0.1:8081/manage`), it will let through domain names that resolve
to those addresses (so if I arranged for `totallynotascam.example.com` to map on to 127.0.0.1,
it would allow through `http://totallynotascam.example.com:8081/manage`).

We can add code to use `socket.getaddrinfo` to resolve the domain name and
and check that the `ipaddress` module recognizes it as a global address.

I don’t know whether this is bulle-proof exactly, and sites that accept URLs from
the general public probably have to be way more paranoid than this these days,
but for the relatively low risk of Linotak editors’ pages, it will probably suffice
for now.
